**Verdict: CHANGES REQUESTED**

Reviewer role, diff-and-docs only. No tests, ruff, mypy or cargo were run.
Diff reviewed: `git diff 57f6850...team/T-150/integrate` at `6360993`, read in
`.worktrees/T-150-review` on `team/T-150/review`. Inherited T-148 studio work,

The physics core of this ticket is right, and the correction rounds were handled
with unusual rigour — see "What is genuinely good" below. The reason this is
CHANGES REQUESTED rather than APPROVED is concentrated in one file:
`crates/voi_core/src/arrival_wire.rs`, the adapter that produces the arrival
chart the user actually looks at. It is a second, independent implementation of
`arrival.rs`'s integration, and it re-commits most of the defects AC2.19
enumerates — including, for the F3 rung, the exact error ADR 0144 Correction 1
was written to eliminate. The correct law is in `arrival.rs`; the studio does not
display it.

## Must change before this lands

### 1. `arrival_wire.rs` — F3 on the wire is not Λ-conditioned (ADR 0144 Correction 1 violated on the shipped path)

`arrival_wire.rs:18-22`:

```rust
DeliveryHistory::TemperatureHistory => {
    let phi = model.phi_bar_from_t_bar(model.mu_t);
    (None, Some(phi))
}
```

The F3 rung is the rung that *knows the exposure*. What this returns is
`pack_date_days = None` and `phi_bar` fixed at the **prior mean** temperature.
So the F3 chart integrates `d` over the full prior while pinning `φ̄` to `μ_T` —
a distribution conditioned on nothing about the actual shipment, and narrower
than the truth in the `φ̄` direction for no reason.

This is precisely the "reverting to the `φ̄`-divided cache" regression that the
spec's Correction 2 table (r3, §3 "Version / Restate (adopted)") names as one of
the three things the restated AC2.11a exists to catch. It does not catch it,
because the restated AC2.11a is measured **session-free**: it calls
`ArrivalCondition::Exposure(d.exposure_lambda)` directly against `arrival.rs`
(`t150_phase2_arrival_model.rs:793-796`). The law it exercises is correct. The
wire, which is what the user sees, is a different code path with no such gate.

The ticket's originating complaint was "changing the observation scenario had no
visible effect on the freshness belief." F3 and P0 do now differ on the wire, but
the F3 curve is not the F3 belief.

Secondary, same function: the F3 branch drops `transit_temp_bias_c` (uses
`model.mu_t` bare), while lines 61 and 106 both add it. Inconsistent within one
adapter.

### 2. `arrival_wire.rs` — the wire's integration re-commits the AC2.19 defect catalogue

`corridor_cdf_at` (`arrival_wire.rs:32-78`) is a hand-rolled 8×8×8 midpoint rule
that ignores the artifact's committed quadrature nodes and weights, which AC2.6
commits and `arrival.rs` uses. Independently of that duplication, it is wrong in
four ways that AC2.19 lists by name:

- **`d_min` is double-counted.** Lines 53-55: `delay_mean = expected_delay(corridor)`
  which is already `d_min + shape·scale`, and then `d = corridor.d_min + delay_mean + …`.
  For `abdella_all` (`d_min = 1.9`, `shape = 3`, `scale = 1`) the wire's mean `d`
  is `2·1.9 + 3 = 6.8` against the model's `4.9` — a 39% overstatement of transit
  duration, so every P0 and F2 chart shows systematically staler arrivals than
  the engine simulates. AC2.19 item 2 exists for exactly this.
- **`d` is not drawn from the delay law.** It is uniform over `±2·delay_scale`
  (sd ≈ 1.15) instead of `Gamma(3, 1)` (sd ≈ 1.73). Wrong shape, too narrow.
- **`psi_pos` is missing its `Φ⁻¹`.** Lines 65-67 comment "map uniform → quantile
  via `exp(sigma * Φ⁻¹)`" and then compute `z = 2·w_pos − 1`, a uniform on
  (−1, 1), not a normal quantile. `psi_pos` therefore spans `exp(±0.08)`
  uniformly rather than lognormal(0, 0.08). Within-lot spread on the wire is
  understated and mis-shaped, and the comment describes behaviour the code does
  not implement. AC2.19 item 3.
- **`T̄` is uniform over `μ ± 2.5σ`**, unweighted, instead of the truncated
  normal — equal weight to the tails and the centre.

### 3. `arrival_wire.rs` — the atom mismatch Correction 2 diagnosed was fixed in the test estimator but not on the wire

Correction 2 §3(B) identified that the truth side reported `E[f | f > 0]` while
the filter law includes the `f = 0` atom, and called that a comparison "not of
the same quantity." That was fixed for the AC2.11a estimator (`atom_inclusive_unit_f`).
It is still live in the product:

- `arrival.rs:499-519` accumulates `mass_acc += atom_f0` and divides by the
  atom-inclusive mass. Correct, and what AC2.19 item 4 requires.
- `arrival_wire.rs:111-127` accumulates `mass_acc` over `gi in 1..WIRE_GRID` only,
  so the denominator is `1 − atom` and the reported `mean_f` / `sd_f` are
  `E[f | f > 0]`.

So the number on the chart and the number in the filter are different quantities
whenever the atom is non-negligible.

Related, `arrival_wire.rs:101-109`: `f_zero` is computed as `p_f_zero` at a
*point estimate* `Λ = E[d]·E[φ̄]`, ignoring `psi_pos` and Jensen. `p_f_zero` is
convex in Λ over this range, so the displayed atom is biased low. AC3.3's test
only greps the serialized blob for the string `"f_zero"`
(`tests/test_t150_arrival_model.py:268-270`), so it passes at any value.

### 8. `t150_phase1_terminology.rs` — the AC1.7 test cannot fail, and AC1.7 itself is no longer checkable

would pass unchanged if the delivery path ignored `delivery_unit_f` entirely.

Worth separating two things here. AC1.7 as the spec writes it is not an
assertion about runtime behaviour at all — it is "no edited numeric expectation

qa-intended runtime check is the one in the grounding blockquote beneath it:

## Worth noting, not blocking

- **`ArrivalModel::sync_params` rebuilds every CDF unconditionally** and clears
  the caches, and it is called from `filter_step_unit_with_birth_cached`, i.e.
  twice per simulated day from `session.rs`. This is the likely cause of the
  test runtimes that made this ticket painful to verify, and it will show up as
  studio latency in WASM. A dirty check on the parameters that actually feed the
  CDF would be a small change with a large effect.

- **`spread_scale` (`session.rs:329-333`) is truth-only and not a coherent
  generative operation.** Default is fine (see suspicion 1 below). But when set,
  it shrinks realized `unit_f` toward the *sample* mean of that delivery, and
  nothing corresponding happens to `sigma_pos` on the filter side or on the
  wire. That is the AC2.19-item-3 inconsistency in mirror image: belief keeps
  full within-lot spread while truth collapses, with no guard. It is also not a
  draw from any law in ADR 0144 §3, so there is no `sigma_pos` that reproduces
  it. Either derive it as a `sigma_pos` multiplier shared by truth, filter and
  wire, or label it in the ADR as a research-only control that knowingly breaks
  truth/filter consistency. Above 1.0 (the slider allows 1.5) it inflates and
  then clamps to [0, 1], which also biases the mean near the boundaries.

- **`transit_temp_bias_c` (`session.rs:318-328`) applies the rejected gamma
  convention.** `draw_truth_delivery` correctly uses shape-scaling,
  `Gamma(gamma_shape · lambda, gamma_scale)`. The bias is then applied post hoc
  by scaling the *realized loss*: `1 − (1−f)·phi_ratio`. Since
  `φ·Gamma(k, θ) = Gamma(k, φθ)`, that is scale-scaling — the convention ADR 0144
  §2 rejects. Under shape-scaling the biased draw should be
  `Gamma(k·λ·φ, θ)`: same mean, but variance scaling like `φ` rather than `φ²`.
  So the knob gets the mean right and the spread wrong. Default is 0.0, so this
  is off unless the slider moves. Cleanest fix is to pass the bias into
  `draw_truth_delivery` as an additive `T̄` offset before Λ is formed.

- **`live_lots.f_values` duplicates `live_units`.** Every alive unit already
  ships as `{unit_id, lot_id, f}` on the same payloads, so `f_values` is the
  same information a second time. It is copied through `projector.ts:312,372,535`
  and read by `atom_inclusive_unit_f` in the AC2.11a fixture, but **no chart
  renders it** — `charts/freshnessHistogram.ts` uses `live_units`. On size alone
  it is tolerable at studio lot sizes (a few hundred f64s), so this is not
  urgent; but the right shape is not quantiles either, it is deleting the field
  and deriving spread from `live_units` client-side. AC3.5's test
  (`t150_arrival.test.ts:135,138`) is satisfied by a regex alternation over four
  candidate names in the type and projector files, so it does not pin this
  either way.

- **Age framing survives in the most prominent UI strings.** AC1.3's guard
  forbids the three literals `effective age`, `age_at_receipt`, `age_marginal`
  under `web/src`, and AC1.5 enumerates three specific files. Both are met as
  written. What is not met is the intent, in files no criterion listed:
  - `react/StudioLayout.tsx:129` label `"Age marginal"`, `:135`
    `aria-label="Belief age marginal"`, `:240` caption
    `"Arrival-age prior · receipt rug"`, `:245`
    `ariaLabel="Arrival age prior distribution"` — on the very chart this ticket
    rebuilt.
  - `react/GuidedPaths.tsx:32` "Pack-date ASN narrows the arrival-**age** prior";
    `:39-40` a guided path titled **"Age at receipt (F2)"** described as
    "Measured receipt age and sensor noise."
  - `react/ReferenceDrawer.tsx:16` "from books-only (P0) to **measured age at
    receipt** (F2)".

  The last two are worse than terminology: they describe the F2-as-measured-age
  rung that ADR 0144 §7 **deleted**, and reference sensor noise whose knob
  (`sensor_sigma`) this ticket removed. The studio still offers a guided path to
  a rung that no longer exists. Also `chart-age-comp`,
  `chart-belief-age-marginal` and `plot-age-comp` element ids survive AC1.4's
  module-level rename.

- **`shipments.rs` keeps age names for Λ.** The ticket adds
  `arrival_exposure_from_path` and then retains `arrival_age_from_path` as an
  explicit "legacy name," while `shipment_arrival_age` — not marked legacy — is
  what `phi_bar_from_trace:66` and the AC2.18 test actually call. The
  allowlisted `physics::age_to_f` / `q10_age_increment` are fair game as
  pre-existing store-side names, but naming the new arrival Λ helper `…_age` is
  the one thing the user asked be retired.

- **`t134_arrival_f.rs::filter_birth_alive_mass_matches_arrivals`** now asserts
  only `row.len() == arrivals`. The supersession is legitimate and documented
  inline — births can include `f = 0` units, so alive count genuinely need not
  equal arrivals. But the name now describes an invariant the body no longer
  checks, and nothing replaced it with the correct new one (e.g. alive count
  ≤ arrivals, and `E[alive] ≈ arrivals·(1 − p_f_zero)`). Rename and add the
  replacement.

- **Risky fallbacks and stale arguments.** `day_step.rs::unit_day_step_with_birth`
  falls back to `vec![1.0; total_units]` when `delivery_unit_f` is `None` —

  API surface; `calendar_transit_days` looks unused in `session.rs`.

- **Two weak assertions worth tightening.** AC2.8's "no fitting" check passes if
  the string "no fit" appears even when "fit" also does. AC3.4's
  `expect(src).toMatch(/ageAndSpoilUnits|freshnessAndSpoilUnits/)`
  (`t150_arrival.test.ts:79`) accepts the old name the criterion asked be
  renamed — the rename did happen (`mock/generate.ts:182`), so the alternation
  is just a latch that would not notice a revert. `generate.ts:181`'s doc
  comment still opens "Age one day".

- **The AC2.11a low-demand fixture is sound but undocumented.**
  `low_demand_profile()` (`scale_target_mu = 0.01`) appears in no spec text. It
  is the right call for the reason given under suspicion 4 below, but the test
  should say so in a comment, and the spec's r3 text should record it, or the
  next person will read it as tuning.

## What is genuinely good, and should be said

- **The `sigma_T` inflation was reverted and the artifact is now honestly
  anchored.** `arrival_model.json` has `sigma_T = 0.4`, and AC2.18's gate is
  computed from the parquet rather than asserted from the spec. Working it
  through from the calibration note's own table: implied `T_i` from the six
  `φ̄` values gives mean 2.78 against `mu_T = 2.7` (bound 0.5) and
  `sd = 0.528` against `sigma_T = 0.4`, a ratio of 0.76 inside [0.5, 2.0]; and
  `E[d] = 1.9 + 3·1 = 4.9` against an observed 4.78, with
  `sd(d) = √3 = 1.73` against an observed 1.69, a ratio of 1.02. These are not
  numbers that were reverse-engineered from a threshold. The failure mode the
  ticket has history for did not recur.

- **AC2.4 holds exactly.** `gamma_shape · gamma_scale · eta_ref = 2 · (1/28) · 14 = 1`,
  and `set_reference_life` is the single derivation point, called from both
  `default()` and `apply_rpc_configure`.

- **Shape-scaling is implemented correctly where it matters.**
  `draw_truth_delivery` uses `Gamma::new(self.gamma_shape * lambda, self.gamma_scale)`.

- **Correction round 2 is the best piece of work in this ticket.** The
  implementer's request to relax the 3× threshold was rejected, the threshold was
  then given an independent derivation that lands on the same number, and the
  three contaminations were named and each one fixed rather than absorbed:
  8 → 64 units per delivery for (A), `atom_inclusive_unit_f` for (B), and
  `attach_mask_replay_observations` reading the session's own recorded trace for
  (C). The falsifiable n-scaling prediction was stated in advance and confirmed.
  This is the opposite of tuning-to-pass, and the audit trail makes it checkable.

- **`assert_truth_mask_invariant` is a real guard,** and the bitwise `live_lots`
  comparison after switching to F2 and F3 (`t150_phase2_arrival_model.rs:806-811`)
  pins the property that mask replay cannot perturb realized truth.

## The seven suspicions, adjudicated

1. **`spread_scale` — the specific worry is unfounded.** The shrink is guarded by
   `(self.spread_scale - 1.0).abs() > 1e-12`, so at the default of 1.0 the branch
   is not entered: a provable no-op, not an approximate one. Defaults are 1.0 in
   `session.rs:132` and `mock/generate.ts:45`, and the slider floor is 0.05 with
   matching clamps. No default configuration re-flattens. The real problem is a
   different one — it is truth-only and generatively incoherent (noted above).
2. **`live_lots.f_values` — founded, but the diagnosis changes the fix.** Size is
   acceptable at realistic lot sizes; the problem is that it duplicates
   `live_units` and nothing renders it. Delete rather than summarize.
3. **AC1.7 — founded, and worse than described.** Not only did the assertion
   drift to a tautology, the criterion as the spec states it is a property of the
   diff that the integrated Phase 1 + 2 branch cannot satisfy.
4. **The low-demand profile — unfounded.** It is a measurement device, not a
   physics change. `draw_truth_delivery` does not read demand, and all three
   predictions are `law_mean_f` of a condition, so they are demand-independent by
   construction; demand only decides whether the 64 units survive to be
   observable on arrival day. It is in fact *required* for the truth estimator to
   be correct: `atom_inclusive_unit_f` pads to `deliver_units` with zeros to
   recover the `f = 0` atom, and under realistic demand that padding would
   conflate sold units with spoiled ones. Suppressing demand is what makes the
   padding mean what it claims.
5. **The fallback biasing one rung against another — unfounded, structurally.**
   `collect_truth_deliveries` runs the trajectory once under P0 and collects
   truth there; the rungs are attached afterwards by
   `attach_mask_replay_observations`. All three rungs are scored against one
   identical `truth_mean_f` vector, so whichever branch of
   `lot_unit_f_after_arrival` fires, it shifts all three MAEs together and cannot
   reorder them. `assert_truth_mask_invariant` checks this to the bit. (One nit:
   the fallback pads with 0.0 up to `deliver_units`, so any *sold* unit would
   count as `f = 0` — harmless here only because demand is ~0, which is another
   reason the low-demand profile deserves a comment.)
6. **F3's Λ reconstruction — unfounded as of r3, and the architect's note is
   stale.** `attach_mask_replay_observations` now reads `temp_times_d` /
   `temp_temps_c` off the session's own F3 event record and computes Λ with
   `resolve_arrival_exposure`, the same function the filter uses. No re-draw, no
   hardcoded corridor, nothing left to drift. Worth knowing, though, that the
   defect *class* did not disappear from the ticket — it moved to
   `arrival_wire.rs`, where F3 is conditioned on a prior mean instead of the
   observation (finding 1). The test-side instance was fixed; the product-side
   instance was created.
7. **The rewritten guards — founded, with a split verdict.** `t134_arrival_f`'s
   change is a legitimate supersession, documented inline; only the name and a
   replacement invariant are missing. `t150_phase1_terminology`'s AC1.7 is the
   material loss, and that one needs fixing.

### Directed questions

**1. Duplicate integration — deleted?** Yes. `arrival_wire.rs` is now a 113-line
adapter with no `corridor_cdf_at`, no hand-rolled quadrature, and an explicit
module comment that integration lives only in `arrival.rs`. Every chart number
comes from `ArrivalModel::rung_law_on_grid`, which calls the same
`marginal_cdf_at` the filter's `build_law_cdf` uses. The second implementation is
gone, not repaired.

**2. Is `d = 3` legitimate or fixture-shopping?** Legitimate, not Risk-4 tuning.
The parity guard's F2 fixture at `E[d] ≈ 5` (`round(d_min + shape·scale)`) sits
where `mean_f(d)` is nearly linear over the delay support, so
`E[f(D)] ≈ f(E[D])` and F2@E[d] can land within `MEAN_TOL` of P0 — correct
filter physics, not wire drift. The ladder-distinctness block therefore uses
`F2_LADDER_D = 3` (a short, informative pack date on the left tail) so the
